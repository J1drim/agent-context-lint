# Official-example conformance corpus

Status: K01 complete for the D16-reviewed GA surface inventory dated 2026-08-02.

Contract: `official-example-conformance-corpus/0.1.0` (independent wire identity; product release
`1.0.0`)

The K01 corpus turns the canonical profile map into a closed, reviewable test inventory. It contains
one positive and one negative D01 fixture for every format capability on all seven GA-required
surfaces. The fixtures are small synthetic repositories derived from official examples: vendor prose
is replaced with inert marker text, while official locations, fields, event inputs, support states,
and uncertainty are retained. No external repository content is copied or executed.

## Coverage contract

The corpus derives its capability set from every `formatSupport` row whose surface belongs to a
`ga-required` profile in `profile-surface-map.v0.json`. The current inventory has 22 capabilities,
14 surface/polarity fixtures, and 44 independently owned capability assertions. Each capability must
reference both polarities and cover the complete adapter matrix:

- supported file locations;
- nested discovery boundaries;
- always-on, path-specific, event-driven, conditional, or model-selected activation;
- profile-owned glob edge cases;
- format-owned import/reference behavior without cross-client transfer;
- explicit ambiguous or undefined precedence; and
- unsupported fields or locations.

“Positive” means the fixture proves the capability's declared support state. It does not convert a
conditional, contradicted, model-selected, `not-listed`, or unknown state into deterministic
support. “Negative” means the paired synthetic input must not be selected; it never invents a vendor
behavior claim. The standalone validator recomputes the exact GA inventory, validates every fixture
through the D01 contract, verifies the D16 review, checks source ownership and immutable revisions,
binds every file by SHA-256, and rejects unused assertions or unmanifested fixture files.

## Provenance and trust boundary

Each fixture has `derivation: official-example`, cites the surface-owned research snapshot, and
repeats an official primary URL. Immutable upstream sources retain their exact revision. Living
documentation retains its retrieval date and mutable-source limitation. D16 remains authoritative
for real-client evidence: K01 cannot promote a blocked observation or a release/version-only probe
into behavioral certainty.

The generator and validator are deterministic, offline, model-free, and read-only except for the
generator's explicitly acknowledged repository-local write mode. They do not invoke clients, read
user configuration, follow fixture symlinks, execute repository commands, or use network/process
capabilities. Referenced files must be ordinary in-root files, are read through stable descriptors,
and are size- and digest-bounded.

## Monthly review ownership

The manifest records:

- primary owner: `@agent-context-lint/profile-reviewers`;
- independent quality owner: `@agent-context-lint/qa-reviewers`;
- cadence: monthly;
- the completed review date; and
- the exact next calendar-month due date.

These aliases are governance placeholders until activated under
[`docs/governance/ownership.md`](../governance/ownership.md). Until then, remote publication remains
disabled. Under the current sole-maintainer policy, the accountable maintainer records the review
and a separate audit agent verifies the exact manifest, fixture digests, and generated bytes. The
agent audit is quality evidence, not an additional human approval; the future aliases above do not
create a second human-review requirement.

At each monthly review:

1. Review every canonical first-party source and the current D16 observation ledger. If live
   research is necessary, use official primary sources only and record URL, retrieval date,
   client/version, assumptions, and documented-versus-observed differences in the owning profile
   record before changing K01.
2. Preserve undocumented, UI-only, model-selected, paid, or version-dependent behavior as
   conditional or unknown. Never resolve uncertainty from release metadata alone.
3. Update the canonical profile map and D16 artifacts through their own contracts first. Then update
   `OFFICIAL_CORPUS_REVIEW_DATE` and `OFFICIAL_CORPUS_NEXT_REVIEW` in the generator.
4. Run the acknowledged generator and inspect all semantic diffs. Generated fixtures are review
   artifacts, not authority:

   ```bash
   pnpm conformance:official:generate
   pnpm conformance:official:validate
   node tools/conformance/validate-official-example-corpus.mjs \
     conformance/official-examples/v0/corpus.json --as-of YYYY-MM-DD
   pnpm test:conformance
   ```

5. Obtain the accountable maintainer's documented review and the separate audit-agent verification.
   Update D16/client fixtures when a real observation contradicts the official example; do not
   silently change the expected outcome in K01.

`--as-of` is explicit so normal builds remain reproducible instead of depending on the wall clock.
The monthly review job or release checklist supplies the review date and fails after
`nextReviewDue`. Ordinary `pnpm check` verifies interval integrity, all digests, and generated-byte
stability without making an old commit time-dependent.

## Updating or investigating failures

Run `pnpm conformance:official:validate` first. Digest or generated-byte failures mean a referenced
artifact changed without a reviewed corpus regeneration. Coverage failures identify the exact
surface/format pair whose positive or negative assertion is missing. Source/revision failures mean a
fixture cites evidence outside its profile owner. Minimize any adapter mismatch into fixture-owned
content; never add an external repository checkout or prepare an upstream contribution.
